### #1779 — verified fixed, behaviourally

The bug: a Markdown KA replicates to peers with operation/assertion metadata present
but **Entities and Triples EMPTY**, because markdown headings import as blank-node section
entities canonicalized to `urn:dkg:ka-skolem:c14n0`, which the receiving SWM validator
rejected as user-authored reserved terms.

Verification imported a real Markdown document with headings — the exact shape that
triggers it — and asserted the **peer** sees content, not just metadata:

```
[PASS] #1779: PEER sees markdown CONTENT triples (not just metadata)
       — 4 content triples on peer in 3021ms
[PASS] #1779: peer graph population comparable to author
       — author=78 quads, peer=76 quads
```

This class of bug cannot be caught by a diff review or an author-side unit test: the write
succeeds, the author looks correct, and only the peer is wrong.

## 2. Also proven (carried over from the pre-release harness)

On a 6-node devnet, both public cells (`public/open` and `public/curated`):

- SWM live sync to a pre-subscribed receiver — exact content match, ~3 ms
- SWM cold backfill — receiver obtains content published *before* it subscribed, ~2-6 ms
- VM publish by the author — confirmed on-chain
- **VM sync to a non-host subscriber** — byte-identical content, delivered by the durable
  peer-sync lane, receiver provably outside the publish ACK set
- Curated gate: non-curator `vm/publish` refused (409)

Known non-blocking defect: **chain-driven reconciliation never advances its watermark**
(`0/1`, `unresolved=1`, permanently). It is redundant — durable peer sync delivers VM — but
completeness accounting stays wrong and there is no fallback if durable sync cannot serve.
Root cause is a *remediation asymmetry*: `dkg-agent-swm-host.ts:3690` gates the active fetch
on `outcome === 'no-swm'`, and `'verified-vm-metadata-pending'` has no case in the switch, so
it falls through to `default:` with no remediation and no negative-caching. The wedged
population is exactly **subscribers that staged SWM but never received VM**.

Do **not** "fix" this by synthesizing evidence — `finalization-handler.ts:1344-1347` forbids
it explicitly, and a locally synthesized `status='confirmed'` is re-served to other peers as
authoritative and is unauditable without a txHash on disk.

## 3. BLOCKER: member → curator SWM never converges on a curated CG

**Newly found. This blocks the curated half of the 10.0.9 claim, and it blocks verifying
#1780 at all.**

### Symptom

On a `public/curated` CG (`accessPolicy=0, publishPolicy=0`), a member (inside the agent
gate) shares to SWM. The share reports **success** locally:

```
[PASS] #1780: MEMBER shared an asset into SWM — status=swm-shared
```

The curator's node **permanently rejects** it:

```
[SharedMemoryHandler] SWM write rejected: Sender Key encrypted workspace payload required
  for private or agent-gated context graph "…/fx-cur-…"
[DKGAgent] SWM substrate receiver dropping share from 12D3KooW… (permanent rejection)
```

Content never converges. The curator then cannot VM-publish it:
`409 VM_PUBLISH_PRECONDITION … is not finalized`.

### What is established

1. The receiver requires encryption for any agent-gated CG, and the rejection is
   **permanent** (`retryable: false`) — `packages/publisher/src/workspace-handler.ts:1021-1027`:
   ```ts
   const requiresEncryptedPayload = hasPrivateAccessPolicy || agentGateAddresses !== null;
   if (requiresEncryptedPayload && !decoded.encryptedPayload && !decoded.senderKeyMessage) { … }
   ```
2. A **public/curated CG is agent-gated.** `getContextGraphAgentGateAddresses`
   (`packages/agent/src/dkg-agent-crypto.ts:473-503`) returns non-null whenever
   `allowedAgents` or `participantAgents` is non-empty — which a curated CG has.
   So `accessPolicy=0` (public) and "requires encrypted SWM" are true simultaneously.
3. The sender uses the **same** condition —
   `packages/publisher/src/workspace-agent-recipients.ts:47`:
   `requiresEncryption = access.hasPrivateAccessPolicy || access.agentAddresses.length > 0`.
4. **Both nodes hold identical agent-gate triples in their stores** (verified by SPARQL):
   `allowedAgent = <member>`, `participantAgent = <curator>`. So this is *not* a metadata
   propagation race — the sender can see it is agent-gated.
5. The sender's encryptor **throws** rather than silently falling back when recipients are
   empty (`dkg-agent-crypto.ts:1164-1169`), so an empty-recipient path would have surfaced
   as a failed share, not a successful one.

### ROOT CAUSE — a sender/receiver condition mismatch

The publisher does not call `resolveWorkspaceAgentRecipients` directly. It calls the agent's
**gated wrapper**, `resolveWorkspaceRecipientsGated`
(`packages/agent/src/dkg-agent-crypto.ts:1134-1151`), wired at
`packages/agent/src/dkg-agent-base.ts:1551`:

```ts
async resolveWorkspaceRecipientsGated(input) {
  if (await this.isContextGraphPublicOnChain(input.contextGraphId, …)) {
    return { requiresEncryption: false, recipients: [] };   // ← PLAINTEXT
  }
  return resolveWorkspaceAgentRecipients(this.store, input); // ← agent-gate aware
}
```

`isContextGraphPublicOnChain` (`dkg-agent-crypto.ts:808-833`) returns true **iff the live
on-chain access policy is `0`**.

So the two sides use *different* conditions:

| | condition | source |
| --- | --- | --- |
| **Sender** | `accessPolicy === 0` → plaintext, **agent gate never consulted** | `dkg-agent-crypto.ts:1137` |
| **Receiver** | `hasPrivateAccessPolicy \|\| agentGateAddresses !== null` → require encryption | `workspace-handler.ts:1021` |

They disagree on exactly one set: **`accessPolicy = 0` AND agent-gated** — which is precisely
the `public/curated` cell. The sender short-circuits to plaintext on "public"; the receiver
demands encryption because the CG is agent-gated; the write is permanently dropped.

**Every member→curator SWM share on a public/curated CG fails this way.** It is deterministic,
not a race, and not a missing operator setup step.

### The fix belongs on the RECEIVER, not the sender

**An attempted sender-side fix was written, tested, and REVERTED. Do not repeat it.**

The obvious move is to make the sender's short-circuit also respect the agent gate (only send
plaintext when public on-chain *and* ungated). That was implemented and it **broke 2 of 38
tests** in `packages/agent/test/swm-public-cg-plaintext.test.ts`, which exist precisely to
prevent it. The failing assertion is `expect(agentLike.store.query.calls).toEqual([])` — the
public path must not even touch the store.

That test file documents the reason, and it is the correct semantics:

> "On a public CG the allowedAgent list governs **publish authority** (`publishPolicy`), not
> **read access**."

and it was itself the fix for a real production bug: on a public CG carrying a
`DKG_ALLOWED_AGENT` list, taking the encrypted path bootstrapped a sender-key handshake that
non-gated recipients rejected ("not DKG-agent gated"), surfacing as **HTTP 500 on promote**.
Encrypting a *public* CG protects nothing — the content is readable by policy — while
reintroducing that failure.

**So the sender is right and the receiver is the inconsistent side.**
`packages/publisher/src/workspace-handler.ts:1021` requires encryption from purely local
state:

```ts
const requiresEncryptedPayload = hasPrivateAccessPolicy || agentGateAddresses !== null;
```

`agentGateAddresses` comes from local store triples — *intent*, not authority — which is
exactly the thing `dkg-agent-crypto.ts:1140-1149` warns against relying on. A CG that is
**public on-chain** should not have its SWM writes rejected for arriving in plaintext.

**Proposed fix:** have the receiver consult the same authority the sender does, so the two
agree by construction — reuse the `isContextGraphPublicOnChain` predicate:

```ts
const requiresEncryptedPayload =
  hasPrivateAccessPolicy
  || (agentGateAddresses !== null && !(await isContextGraphPublicOnChain(contextGraphId)));
```

with the **same fail-closed discipline**: only a LIVE public proof (policy `0`) may relax the
requirement; `unknown` / `unregistered` / RPC flake must keep requiring encryption. Otherwise
a stale or unresolvable probe becomes a plaintext-acceptance hole.

**Risks to weigh before implementing:**

- The receiver is in `packages/publisher` and may not have a cheap chain handle; this likely
  needs a resolver injected the way the sender's is (`setWorkspaceAgentRecipientResolver`).
- It relaxes a security check. It is only safe because "public on-chain" means the content has
  no confidentiality requirement at all — that reasoning must hold, and be reviewed by someone
  who owns this subsystem.
- Rollout is asymmetric: old receivers keep rejecting plaintext on gated CGs until upgraded, so
  curated CGs stay broken for mixed-version fleets until the receiver fix is widely deployed.

**This is a security-adjacent decision and should not be made under release pressure.** The
finding, the reproduction, and both candidate fixes are documented here; the call belongs to a
subsystem owner.

### Why nobody caught it

- Every previous harness had the **curator** (also the CG owner) do the sharing. That is a
  local write; no gossip is involved, so it always passed.
- The member→curator direction is the one the curated flow depends on, and nothing exercised it.
- PR #1780's own notes flag the gap: *"Two-node devnet share → curator-publish (recommend
  before release)"* — never done.

## 4. A documentation defect that caused a false-passing test

The OT-RFC-64 handoff states:

> "`accessPolicy` governs read, SWM submission… `publishPolicy` governs VM transaction
> admission only. Therefore public/open and public/curated have identical SWM authorization
> behavior."

**That is not what the code does.** A curated CG is agent-gated, and
`resolveWorkspaceGossipSigningAgent` (`dkg-agent-crypto.ts:2505`) refuses an SWM gossip write
from any agent outside the gate:

> `Cannot gossip SWM write for agent-gated context graph "…": no local allowed signing agent key`

A non-curator can `wm-seal` **locally** (create returns 200, `status: 'wm-sealed'`) but the
write never gossips. Public/open and public/curated therefore do **not** have identical SWM
authorization behavior.

The harness previously asserted `"non-curator MAY stage to SWM"` and passed — because it only
checked that the create returned 200, never touching the gossip path. That check has been
replaced with two that can actually fail: the create must stay `wm-sealed`, **and** an
explicit `swm/share` by a non-curator must be refused by the agent gate.

## 5. What can and cannot be claimed today

### CAN claim

- Markdown Knowledge Assets now replicate to peers with content intact (#1779), verified
  end-to-end on devnet.
- `public/open` Context Graphs converge on SWM (live and cold-backfill) and on finalized VM
  for subscribers, at small scale on one machine.

### CANNOT claim

- **"Public CGs sync reliably"** — the curated cell's member→curator SWM path is broken (§3).
- **#1780 is fixed** — merged and unit-tested, but unverifiable end-to-end until §3 is fixed.
- **Bounded delivery latency.** A subscriber that misses the live window and has already
  synced cleanly may wait up to ~10 min (`SYNC_RECONCILER_INTERVAL_MS` 5 min /
  `SYNC_STALENESS_THRESHOLD_MS` 10 min, `dkg-agent-constants.ts:175,183`). Eventual
  consistency, not an SLA.
- **Anything at scale or under failure.** The resilience phase (`RESILIENCE=1`: 25 KAs ×
  40 quads × 512B literals, full-corpus reconstruction by a fresh subscriber, idempotent
  repeated reconciliation, author-offline convergence) is **written but not yet run**.
- **Anything cross-machine.** Everything here is localhost. Note a devnet with ≤4 nodes
  cannot even produce a non-host subscriber (ACK quorum is 3), which is how the VM
  reconcile defect stayed hidden.
- **The reconcile watermark as a health signal.** It sits at 0 with VM fully present.
  Monitoring must not read `watermark < head` as "sync broken".
