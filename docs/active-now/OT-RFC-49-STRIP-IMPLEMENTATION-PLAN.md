## Corrections from adversarial review (authoritative over the plan body)

1. **M1 is NOT "additive / independent / ships today" — it is a semantic rewrite with a migration tail.** The current writer (`emitPublicProjectionAfterPublish`, dkg-agent-publish.ts:1312-1345) writes the DCAT entry into a *separate discovery CG* (`publicProjectionContextGraphId`) **after** publish confirms. M1 moves it to a *before-publish* injection into the private CG's **own** root, dropping `committedRoot`. Retirement + new injection MUST land together. Reclassify size **M → M+**, and it is **not** dependency-free.

2. **Confirm the publish path FIRST — it is a hard predecessor to M1, not a parallel open question.** There are **three** publish paths, each with its own seal: `_publish` (seal at :1214), `publishAsync` (subtracted-slice seal), and `assertionFinalize` (separate root at :1733). M1 only attaches to `_publish`. Determine which path the target private CGs actually use; the root-consistency proof must be replicated **per path in use**, or the entry is dropped / the seal-compare fires.

3. **Pin the RandomSampling private-CG exclusion in M5, not M7.** Excluding `accessPolicy!=0` CGs from the public draw is a **hard co-requisite** of relaxing `CuratedCGRequiresCiphertextCommitment` (M5's own test gate requires it). Leaving it in M7 creates a dead-zone where private data is unsampled *and* still core-custodied — unaccountable. Move it into M5.

4. **M2's `/_catalog` data-path exclusion is REQUIRED, not optional.** `readDurableDataPage`'s filter `graph.startsWith(cgPrefix + "/")` sweeps `…/_catalog` by default (graph-plan.ts:235); without an explicit exclusion the gated data phase also emits catalog quads, causing cursor desync. Make the bounding query exact: release **only** the `_catalog` named graph.

5. **Two missing pieces to add as work items:**
   - **Backfill / migration of already-published projection entries.** Every private CG published under today's writer has its entry in the *old discovery CG*, not its `_catalog`. The instant M1 retires that writer, those entries orphan and `_catalog` is empty until each CG re-publishes — discovery silently regresses for the whole existing corpus. Add a re-projection/backfill step.
   - **Anchor-roster privacy on the public beacon (M3).** Carrying `{memberAgentAddress, peerId, multiaddrs}` of a private CG's anchor set on the public gossip beacon leaks the membership roster. This needs an explicit decision, not just a wire-compat note.

6. **Intermediate-state hazards to respect (test ordering + rollout):**

## M1 path-confirmation result (resolved — supersedes the M1 body's attach point)

The review made "confirm the publish path" a hard predecessor to M1. **Done — and it materially changes M1.** Traced in code:

- **The product path is the finalized-assertion path, not `_publish`.** The daemon HTTP API publishes a KA to VM via `agent.publishFromFinalizedAssertion` — `POST …/vm/publish` (`knowledge-assets.ts:923`) and the atomic create+publish (`:622`), each after `agent.assertion.finalize`. The plan body's attach point `_publish:1214` is the **SDK/programmatic** path only (`agent.publish()`), not what the daemon runs.
- **Two genuinely distinct seal points.** `assertion.finalize` (`assertionFinalize:1616`) seals at `merkleRoot = computeFlatKCRoot(allSkolemizedQuads, [])` (`:1733`); `publishFromFinalizedAssertion` (`:2881`) reloads the sealed SWM slice and calls `publisher.publish` **directly** (not `_publish`) with the seal as `precomputedAttestation.expectedMerkleRoot` (`~:3088`). The SDK `_publish` path computes its **own** seal via `_buildPrecomputedAttestationForSelection` (`~:1214`). So M1 has **two attach points** (`assertionFinalize` for the product path, `_publish` for the SDK path), each needing its own root-consistency proof; `publishAsync` is a third path only if async captures must carry the floor.
- **Primary attach point is `assertionFinalize`.** The catalog quads must be injected into the finalized-assertion content **before** the seal at `:1733` **and** persisted into the slice `publishFromFinalizedAssertion` reloads — otherwise the seal and the reload disagree and the `expectedMerkleRoot` compare fires.
- **NEW open blocker for the product path (was not in the plan):** the finalize path handles private content **differently** from `_publish`. `assertionFinalize` seals everything as one set (`computeFlatKCRoot(…, [])`, empty private-roots arg), and `publishFromFinalizedAssertion`'s `publisher.publish` call site (`:3079-3099`) does **not** pass the `encryptInlinePayload`/`encryptInlineChunked` emitters that `_publish` resolves for curated CGs (the comment says encryption is "wired through … via `publishFromSharedMemory`"). **Before M1 can inject a *public* catalog entry on the product path, the finalize→`publishFromSharedMemory`→`publisher.publish` private-content flow (where the public/private split and curated encryption actually happen) must be traced end-to-end.** This is M1's true first task and is not yet done.

**Net:** M1 is confirmed as **larger than "M"** — two attach points + a per-path root-consistency proof + the finalize-path private-content trace + the migration/backfill tail. It is still the right first slice, but "ships today" is wrong; the next concrete step is the finalize-path private-content trace.

## M1 finalize-path trace result — the combined model is a DEEP change on the product path

Traced `publishFromFinalizedAssertion` → `agent.publishFromSharedMemory` → `publisher.publish` end-to-end (3 agents, re-verified, both tracers agree). Verdict: **deep-change**, decomposed:

- **Resolved (not a gap):** the product path DOES encrypt curated content — emitters are resolved one layer below the call site, in `agent.publishFromSharedMemory` (`dkg-agent-publish.ts:3513/3528`, forwarded :3552-3553), gated on access policy.
- **The own-root + verifiability/consistency half is a CLEAN slot-in (zero core change):** write the floor quads (combined model, `committedRoot` omitted) into the **single** WM assertion graph via `assertion.write` *before* `assertion.finalize`. They survive the reserved-subject filter (a UAL isn't reserved), are hashed into the seal `computeFlatKCRoot(allSkolemizedQuads, [])` (:1733), become a bound `rootEntity`, are promoted to SWM, reloaded by subject in `publishFromSharedMemory`, and recompute byte-identically (`canonical-publish-payload.ts:51`; empty `privateRoots` ⇒ root = `V10MerkleTree(publicQuads).root`). They MUST go in the one promoted `wmGraphUri` — a sibling `_catalog` graph would NOT be promoted/reloaded.
- **The "served as plaintext by cores" half is a DEEP change (the real blocker):** the product/finalize path has **NO public/private partition** — for a private CG it AEAD-encrypts the **entire** reloaded plaintext blob (`dkg-publisher.ts:1989-2022`). So injected catalog quads get encrypted with everything else; cores receive **opaque ciphertext**, not servable plaintext DCAT. Making the catalog subset plaintext-servable requires: a NEW partition captured **at reload time** (read the `?g` binding in the CONSTRUCT — graph identity is gone by the time `publish()` runs, `dkg-publisher.ts:1328`); a plaintext public sink for a *curated* KC (`publicSnapshotStore` is SDK-path-only today); **and wire/contract changes** — the V10 ACK + on-chain `PublishParams` must represent a **MIXED payload** (plaintext public segment + ciphertext chunks under one `batchId`/`merkleRoot`+`ciphertextChunksRoot`), **not verified to be expressible today**. Plus core-side servability of a plaintext subset of a curated KC is an open RFC-38 LU-6 hosting question.

**Consequence — M1 forks, and "in the CG's own root" naturally belongs with the strip, not before it:**

- **Outsider discoverability requires plaintext-servable-by-cores.** The combined model's cheap half (quads in the root) does NOT deliver that on its own — the quads would be inside the encrypted blob, readable only by members. So the cheap half alone is pointless for discovery.
- **The already-wired separate-KA emitter** (`emitPublicProjectionAfterPublish`, :1312) publishes the floor as a standalone PUBLIC KA with a `dkg:committedRoot` back-reference — delivering discoverability + verifiable linkage with **zero core/contract change** — but it runs **only on the SDK `_publish` path** (:1295), never on the product/finalize path.
- **Recommended M1 (revised):** *extend the existing separate-KA DCAT emitter to fire on the product/finalize path.* Small, no contract, delivers outsider discoverability + `committedRoot`-verifiability on the real path. Accept the standalone discovery KA for now. **Fold the "entry in the CG's own root" (mixed-payload) combined model into the strip (M5/M6)**, where the contract/ACK/payload representation is being changed anyway and a plaintext-public + ciphertext-private mixed KC becomes a natural addition. This is the pragmatic resolution of the earlier "two CGs feel weird" objection: keep one verifiable back-reference now; unify into one root only when the contract is already open.

## UPDATE — mixed payload IS expressible with NO contract change (decision: build the combined model)

The "deep / contract-blocked" fear above is **resolved against the contract**. Verified:

- **The contract does not tie ciphertext to leaves.** `KnowledgeAssetsLifecycle.sol:701-713` requires a curated KC to carry *a* non-zero `(ciphertextChunksRoot, ciphertextChunkCount)` — nothing more. No constraint relates `ciphertextChunkCount` to `merkleLeafCount`. The ACK digest (`:644-663`) binds both counts **independently**.
- **Sampling never touches the public leaves.** For a curated KC the prover verifies against `getLatestCiphertextChunksRoot` with `leafCount = getCiphertextChunkCount` (`RandomSampling.sol:304-309`, draw at `:631`), and `_pickWeightedChallenge` skips any curated KA with `getCiphertextChunkCount == 0` (`:617`). So challenges only ever land on the **private ciphertext chunks** — the plaintext public catalog leaves are in `merkleRoot` but **not** in the chunk tree, so they are never sampled.

**Therefore the combined model is a TS-only change** (no redeploy, no audit): `merkleRoot` over all plaintext leaves (catalog + private) for verifiability; `ciphertextChunksRoot`/count over **only** the private chunks for custody/sampling; catalog quads plaintext in `publicSnapshotStore`, servable by cores. Build sequence (all TS):

1. `contextGraphCatalogUri` helper + inject the catalog floor quads (combined model, no `committedRoot`) into the **single** WM assertion graph before `assertion.finalize` — clean slot-in, in `merkleRoot`.
2. Reload-time partition in `publisher.publishFromSharedMemory`: identify catalog quads (by subject == CG UAL / the floor predicates), carry them as a `publicCatalogQuads` subset.
3. Encryption exclusion: feed **only** the private quads to `encryptInlinePayload`/`encryptInlineChunked` ⇒ `ciphertextChunksRoot` over private chunks only; include the catalog leaves in `merkleRoot` (so the seal is unchanged).
4. Plaintext public sink: write the catalog subset to `publicSnapshotStore` even for a curated KC (today SDK-path-only).
5. `byteSize`/pricing reflects the ciphertext (private) bytes; the small public catalog is not priced as retained ciphertext.
6. Core-side servability of the plaintext catalog subset of a curated KC (this **is** M2's facet-scoped open-serve).

**Two TS-level risks still to assess (not contract):** (a) adding the CG's own UAL as a bound `rootEntity` in its own publish may shift KA-manifest count / token labeling (RS prover ka-extractor) — `canonical-publish-payload.ts:30-45` builds one manifest entry per skolemize root; assess before wiring the injection. (b) `byteSize`/pricing semantics when the priced ciphertext no longer covers every leaf.

## OT-RFC-49 Implementation Plan (full body) — Ciphertext Strip + Member-Anchor Tier + Combined Catalog Entry

Status branch: `feat/rfc49-public-projection` (dkg-v10 10.0.0-rc.17). Author: tech lead. Audience: OriginTrail engineers.

---

## 1. Executive summary

OT-RFC-49 ("hosting follows access") moves a private context graph's private content (live SWM + VM private payload) off core nodes entirely. Cores host **only** the public catalog entry — a DCAT dataset record in the CG's own `_catalog` subgraph, committed inside the CG's own VM merkle root. The private bytes are custodied by **member anchors**. Public CGs are unchanged.

What actually ships, and the order:

1. **M1 — Combined catalog entry (additive, discoverability).** Attach the DCAT entry into the private CG's own publish as public quads in `_catalog`, committed inside the CG's own root. Retire the separate-KA projection model. **Independent of everything else.** Ships alone.
2. **M2 — Facet-scoped open-serve.** A new `catalog` SyncPhase the responder serves without the private-sync allowlist gate, bounded to exactly the `_catalog` named graph. Makes M1 discoverable by non-members. Depends on M1's writer landing in `_catalog`.
3. **M3 — Minimum anchor custody (off-chain Phase 1).** Flip the host-mode role-gate so member anchors engage the existing store, exempt anchored chunk sets from eviction, reuse the existing chunk-serving path, plus the §5.7 reliability fixes (catch-up v2, SenderRekey, evidence-gated loss). **This is the destination that the strip routes to — it must exist before M4/M6 can route anywhere.**
4. **M4 — Stop shipping SWM live ciphertext to cores.** Member-scope the SWM gossip; cores never subscribe/store private envelopes. Requires M3 (member-to-member catchup is the new backfill).
5. **M5 — Contract: accept member-anchor ACKs + relax ciphertext requirement.** `_verifySignatures` becomes CG-aware; the curated-ciphertext-commitment gate relaxes. **Redeploy + external audit. The long pole.**
6. **M6 — Stop shipping VM payload ciphertext to cores (route to anchors).** Re-point the StorageACK collection at the anchor set. Requires M3 (custody) + M5 (chain accepts anchor ACKs).
7. **M7 — Anchor economy (deferred).** On-chain anchor registry, ACK v3, escrow/scoped-sampling/bond/slash. Audit center of gravity. Explicitly off the critical path.

**The hard truth about scope:**

- **The anchor custody tier is 100% greenfield.** Grep for `availabilityClass|anchorRegistry|anchorSet|setVersion|isAnchor|anchorStake|hostingPolicy` across `packages/*/src` and `evm-module/contracts` returns **zero hits** (verified this session). Every sentence in the RFC that says "route to anchors" maps to a destination that must be **built first**. There is no shortcut.
- **The contract change needs redeploy + external audit.** `_verifySignatures` is the protocol's core trust boundary (who may attest a publish). Branching the sharding-table membership gate is a high-sensitivity change, no proxy upgrade (redeploy + reinit), and it is consensus-critical: the ACK digest must stay byte-identical between off-chain sign and on-chain verify.
- **This is a multi-milestone program, not a sprint.** Realistic shape: M1+M2 are a 1–2 week additive slice shippable immediately. M3+M4 (off-chain Phase 1) is ~6–8 weeks dominated by the §5.7 reliability/ratchet work. M5+M6+M7 (the on-chain economy) is the 4–5 month, 2-engineer-plus-audit effort the RFC and our memory estimate already name.

**What stays unchanged in every milestone:** public CGs (accessPolicy=0) — cores still host, sample, ACK. Every milestone must prove a no-op delta for public CGs.

```

   ships ALONE today                            unit-only, no chain

M3 (min anchor custody, off-chain) ─────┬────► M4 (strip SWM ciphertext to cores)

M5 (contract: anchor ACKs + relax) ─────────► M6
   redeploy + EXTERNAL AUDIT                     M6 cannot route ACKs to anchors
   the long pole                                 until chain accepts them

M5 + M3 ────────────────────────────────────► M7 (anchor economy: escrow/sampling/bond)
                                                 deferred; audit center of gravity
```

**Key ordering facts to internalize:**

- **M1 is independent of the strip.** It is purely additive: it attaches public quads into a publish that already happens. It does not touch SWM, ciphertext, ACKs, or contracts. It can ship while everything below is still on the drawing board.
- **M2 depends only on M1.** The open-serve carve-out is a no-op (serves nothing) until the `_catalog` graph is actually populated by M1's writer.
- **The strip's "route private payload to anchors" is BLOCKED on M3 (the anchor custody tier) existing.** Until anchors can durably hold and serve the bytes, the only honest strip is "cores stop holding private ciphertext; members self-host" — and even that needs a member-to-member late-join catchup story, which is the §5.7 work inside M3. There is no version of M4/M6 that ships before M3.
- **M6 has a double prerequisite: M3 (somewhere to put the bytes) AND M5 (a chain that accepts anchor-signed ACKs).** Re-pointing ACK collection at members before the contract accepts member signers means every private publish reverts with `SignerIsNotNodeOperator`.
- **M7 is deferrable by design.** Durable member custody + serving (M3) require zero contract changes. The economy (registry, ACK v3, escrow, bond, sampling) is a separate, audited effort and must not sit on the strip's critical path.

## 3. Milestones

### M1 — Combined catalog entry (attach DCAT entry into the private CG's own publish)

**Goal.** A private CG publish embeds its DCAT catalog entry as public quads in a `_catalog` subgraph, committed inside the CG's own merkle root (not a separate facet KA). Retire the separate-KA projection model.

**Scope — in:** the sync publish path (`_publish`); the new `_catalog` URI helper; reuse of the existing builder; retirement of the after-publish hook and its config field.
**Scope — out:** the async/EPCIS/Kafka capture path (`publishAsync`) — lower priority, fold in only if those captures must carry the catalog floor; the finalized-assertion path (`assertionFinalize`) — confirm first whether target private CGs use it.

**Exact change sites.**
- `packages/core/src/constants.ts` :: **NEW** `contextGraphCatalogUri(contextGraphId)` → `did:dkg:context-graph:${contextGraphId}/_catalog`. Add near `contextGraphSubGraphUri` (~326). Must follow the reserved-name convention (`validateSubGraphName` at ~379 reserves `_`-prefixed names, so `_catalog` cannot collide). **This is the only genuinely-new core symbol.**
- `packages/agent/src/dkg-agent-publish.ts` :: `_publish` (1173–1284). **THE primary attach point.** Inject catalog quads into `quads` **before** line 1214 (the `_buildPrecomputedAttestationForSelection` seal), gated on `await this.isPrivateContextGraph(contextGraphId)`. Because the seal merkle (1214) and the publish merkle (`this.publisher.publish` at 1268 → `canonicalPublishPayload` at publisher 1834) consume the **identical array**, injecting once lands the entry in both roots and keeps the `expectedMerkleRoot` guard consistent. This is the only place where one injection satisfies both roots.
- `packages/agent/src/context-graph-public-projection.ts` :: `buildPublicProjection` (90–134). **Reuse unchanged.** Call with `accessPolicy:'private'`, `graph: contextGraphCatalogUri(cg)`, **NO `committedRoot`** — lines 109–115 already short-circuit the `dkg:committedRoot` quad (verifiability is intrinsic, the entry is in the CG's own root).

**New components.**
- `contextGraphCatalogUri` (constants.ts).
- A catalog-injection helper on the agent (`buildOwnCatalogEntryQuads(contextGraphId)` or inline): checks `isPrivateContextGraph`; derives the CG UAL subject **structurally** (`did:dkg:context-graph:${contextGraphId}` per cg-resolve.ts:509 — required because injection happens **before** publish, so we cannot read `result.ual`); calls `buildPublicProjection` with no `committedRoot`; returns quads to merge.
- An idempotency/dedup guard so repeated CG publishes don't double-write or diverge the catalog floor (rely on canonical skolemize+dedupe or an explicit "already present" check). **Decision required** (see §6).

**Prerequisites.** `contextGraphCatalogUri` exported from `@origintrail-official/dkg-core` before either attach site imports it. `buildPublicProjection` + DCAT/dkg ontology constants (genesis.ts 245–265) already exist — no new ontology terms. `isPrivateContextGraph` already a DKGAgent method.

**Test gates.**
- **Unit (central) — ROOT-CONSISTENCY:** prove the catalog quads land in **both** the seal merkle (agent ~1214) and the publisher recompute (`kcMerkleRoot`, publisher 1834/1879) so the `expectedMerkleRoot` guard at **publisher 2490–2497 does NOT fire**. Assert byte-identical `kcMerkleRoot` on both sides after injection.
- Unit: `contextGraphCatalogUri` returns `.../_catalog`, passes `assertSafeIri`, is rejected by `validateSubGraphName` as reserved.
- Unit: `_publish` injects the floor **only** for private CGs, omits `committedRoot`, targets `_catalog`; public CGs get **zero** catalog quads.
- Regression: `canonical-publish-payload.test.ts` + assertion-seal tests stay green (skolemize places the CG-UAL subject in its own manifest entry without disturbing other roots).
- Retirement: assert `emitPublicProjectionAfterPublish` no longer fires; no write to a separate discovery CG. (Note: there is currently no unit test for this method — low test-debt, low existing coverage.)
- **Hardhat integration:** a private CG publish with the embedded `_catalog` entry mints with a merkleRoot the chain accepts and the seal preflight passes against the live publisher recompute. Only a V10 hardhat publish exercises `buildAuthorAttestationTypedData` + on-chain accept with the catalog quads present.

**Risk.** **CENTRAL:** the entry must be in both the seal payload and the publish payload. The mechanical safety holds **only because `_publish` feeds one array to both** — any refactor that branches the array between 1214 and 1268 reintroduces the `expectedMerkleRoot` divergence. Secondary: UAL must be derived structurally (not from `result.ual`); a structural-vs-on-chain-canonical UAL mismatch keys the entry on the wrong subject. Disclosure invariant: `_catalog` quads are public for a private CG — the injection must pull **only** the typed floor on the CG-UAL subject, never private quads or extra subjects.

**Size: M.** (Attach + helper + retirement sweep + the root-consistency proof.)

## 4. Contract & audit gates

**What triggers a redeploy.** Any change to `KnowledgeAssetsLifecycle.sol`, `ContextGraphs(+Storage).sol`, or `RandomSampling.sol`. These contracts are **redeploy + reinit (no proxy upgrade)**. M5, M7 trigger redeploys. M1–M4 and M6's off-chain legs do not (M6's *acceptance* of anchor ACKs depends on M5's redeploy, but M6's publisher code does not itself trigger one).

**What needs external audit.**
- **M5 — mandatory.** `_verifySignature` signer-eligibility is the core trust boundary (who may attest a publish). Branching the sharding-table membership gate is exactly the high-sensitivity class prior audit findings clustered around. Do not ship to mainnet without a fresh external audit.
- **M7 — mandatory and larger.** Token-moving surface (escrow, bond, slash, scoped sampling) is the audit center of gravity.
- M1–M4, M6 off-chain: internal review + the existing security-review skill on the diff; no external audit (no trust-boundary change on-chain).

**Migration of existing curated CGs.** Today every private CG with paid KCs **has** a ciphertext commitment and participates in the public curated draw (RFC-39 Phase B). Any of {optional, forbidden, anchored-only} changes its sampling treatment. Because the contract is redeploy + reinit (no proxy), existing CG state **persists** in `ContextGraphStorage` across the redeploy and must remain interpretable — so:
- Add an explicit posture flag (grandfather vs migrate) on the `ContextGraph` struct (slot-0 spare bytes).
- Lock a signed-off migration posture (RFC-49 §5.5.7 accepts migration-from-network as legitimate) — otherwise it is a silent reward rug for current curated publishers.
- A hardhat test must prove a pre-redeploy curated CG still resolves and is treated per its posture after redeploy+reinit.
- Consumers of the **retired** separate discovery-CG (DCAT_CATALOG network browse, Oracle catalogue) must migrate to reading `_catalog` subgraphs (M1/M2). Inventory these before M1's retirement lands.

**Irreversibility.** Contract redeploys on mainnet are irreversible. Relaxing `CuratedCGRequiresCiphertextCommitment` incorrectly could let **public** KCs skip commitments — the gate keys off `accessPolicy`/`getIsCurated` (private axis), so the relaxation must be proven private-only by test.

## 6. Open risks & decisions (load-bearing)

1. **Root-consistency at finalize vs publish (M1).** The catalog entry must be in **both** the seal merkle (agent ~1214) and the publisher recompute (publisher 1834/1879), or the `expectedMerkleRoot` guard at **publisher 2490–2493** (verified) throws. The fix is mechanically safe **only because `_publish` feeds one array to both** — any future refactor that branches the array between 1214 and 1268 reintroduces the divergence. **Decision/confirm:** which publish path do target private CGs actually use — direct `_publish`, `publishAsync` (async seal recomputes against live confirmed state; idempotency hazard), or `assertionFinalize` (separate seal at ~1733)? If finalized assertions, the entry must also be present before 1733. **Confirm before coding M1's attach.**

2. **The facet-bounding query (M2) — the exfiltration boundary.** `readDurableCatalogPage` MUST query **exactly** `did:dkg:context-graph:<cgId>/_catalog` via `readGraphRowsPage` (one `GRAPH <iri>` clause), **never** the `cgPrefix`-startsWith expansion of `readDurableDataPage` (which sweeps every data subgraph). **The auth carve-out and the bounded reader must land in the same change** — never the auth bypass alone. **Decision:** single-source the `_catalog` URI helper across M1 (writer) and M2 (reader) so they cannot drift; treat `_catalog` as read-only-from-projection and reject ad-hoc writes.

3. **Minimum-anchor vs full-economy (M3 vs M7).** Phase 1 ships with NO bond/escrow/sampling — availability is accountability-by-attribution only. A colluding membership can anchor-then-refuse, or anchor garbage; a 1-anchor/single-org set carries no independent root attestation. **Decision:** this is acceptable for the §2.4 consortium class (members hosting their own data) **provided tooling surfaces it as self-attestation.** Reward forfeiture (M7 escrow) and slashing (M7 bond) are the real enforcement and are deliberately deferred. Lock the product statement that Phase 1 is cooperative, pinned-version-consortium-grade, not an adversarial guarantee.

4. **Semantics of "private" on-chain (M5).** Is private = "commitment optional" (lower blast radius, migration step) or "commitment forbidden" (Rev-2 end state)? They have different revert behavior and different sampling coupling. **Decision required before the M5 hardhat tests lock semantics.** Coupled: relaxing the commitment without excluding private CGs from the public draw leaves a silent half-state — ship the exclusion together.

5. **§5.7 reliability is a hard co-requisite, not optional polish (M3).** Demoting/removing core staging without catch-up-v2 + SenderRekey + evidence-gated loss "bricks the ratchet" (skip-cache=64, outbox cliff 24h). **This is the schedule driver for off-chain Phase 1** — start it first and unconditionally.

6. **Testnet/devnet availability.** M1 and M2 are provable at unit level + one hardhat publish (M1's root-consistency on-chain proof). M3/M4/M6 need a multi-node devnet to prove zero-leak (G1), no-brick recovery (G2), honest-loss (G3), cold-start (G4), and serving (G5) — these are not unit-provable. M5/M7 need the hardhat harness (`packages/chain/test/hardhat-harness.ts`). **Decision:** confirm a 2-anchor + ≥1 instrumented-third-party-core devnet topology is available before M3 exits design; the zero-leak gate is the whole point of the strip and cannot be faked at unit level.

7. **Retirement sweep scope (M1).** Removing `publicProjectionContextGraphId` / `emitPublicProjectionAfterPublish` may break daemon/CLI/node-config wiring that sets the field. **A grep-and-remove sweep is required**, and any consumer relying on the separate discovery-CG (DCAT_CATALOG network browse, Oracle catalogue) must migrate to reading `_catalog` subgraphs first. **Decision:** keep both models behind a flag during migration, or hard-cutover? Recommend a brief flagged overlap so discovery consumers migrate before the separate-CG writer disappears.
