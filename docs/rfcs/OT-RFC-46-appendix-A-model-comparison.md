# DKG v10 Knowledge Asset Storage: Model 1 (Exclusive-Entity / 2-Graph) vs Model 2 (Overlapping KAs / Per-KA Named Graph)

## The Fork

The team must choose how Knowledge Assets are physically stored and identified. **Model 1** (the v10 SPEC's target, implemented via OT-RFC-46) collapses every KA's triples into ~2 named graphs per contextGraph and forbids more than one KA per root entity — KA→triple membership becomes a recorded fact (`dkg:rootEntity` in `_meta`, or an in-bucket `dkg:knowledgeAsset <ual>` backlink). **Model 2** (the current per-KA-graph implementation) keeps one named graph per KA, so the quad's 4th term carries per-QUAD membership and any number of independent KAs can describe the same entity.

The one headline tradeoff: **per-quad context XOR 2-graph efficiency.** The named-graph 4th term is the *only* carrier that cleanly separates two KAs' differing facts about a shared subject (KEY SHARED FACT). Model 1 gives it up to win graph-count, discovery, and whole-corpus analytics; Model 2 keeps it to win multi-source provenance, isolation, and reversibility. A crucial fairness caveat threaded throughout: "Model 2" names two things — the **current per-KA-graph implementation** (genuine per-quad separation) and **OT-RFC-46's bucket variant** of Model 1, which itself concedes its membership tag is "deliberately coarser" (per-subject, not per-statement) and therefore re-incurs Model 1's shared-subject conflation. RFC-46 is a performance refactor of Model 1, *not* a way to get both overlap and cheap reads.

> **Framing correction — the codebase is already MIXED today (read every table with this in mind).** "Model 2 = what we have, Model 1 = the change" is only half true. **WM and VM mint one named graph per KA today** (Model-2-shaped — RFC-46:43-45). But **SWM and the published/finalized data graph are *already* shared buckets**, read via the `STRSTARTS` carve-out (`resolveKA`, `dkg-query-engine.ts:739`; the consensus-critical RS gather, `ka-extractor.ts:244-246`) — i.e. **Model-1-shaped, in production, now.** Accurate framing: *Model 2 is what WM/VM have; Model 1 is what SWM/published-data already have; RFC-46 unifies everything onto Model 1.* This tempers Model 2's "no-migration" edge below.
>
> **A real third option: the choice need not be global — it can be per-layer.** Keep per-KA graphs where isolation/overlap matter (WM private drafts; any layer that must support multi-source overlap), and shared buckets where whole-corpus analytics dominate (published VM data). The published layer already runs Model 1; WM already runs Model 2. A per-layer policy may fit the real requirements better than forcing one model everywhere — and it is *not* on the scorecard, which scores a single global choice.

## 1. UX & Collaboration

| Dimension | Model 1 (exclusive-entity / 2-graph) | Model 2 (per-KA named graph) | Verdict |
|---|---|---|---|
| **Mental model** | entity == KA: one canonical record per entity. Crisp, unambiguous "the description of X." | KA == authored assertion: a KA is "what author A says about X," many can coexist. | **Model 1** (crispness) — judgment; clean single source of truth per entity. |
| **Add a fact (permission + autonomy)** | Find the owning `kaId` and do an owner-only UPDATE; a 2nd publish on an existing rootEntity is rejected (`validation.ts:75-86`). Non-owners may only *link* in a separate entity (SPEC:129). | Publish a new KA, permissionlessly; any agent may assert (SPEC:19). | **Model 2** — owner-only update is a hard gate (RFC-45 §1); Model 2 needs no owner consent. |
| **Multi-party co-description, discovery, provenance, retraction** | One party owns the entity; others must publish separate linking entities (SPEC:129); the point-read seek misses those links; retraction is owner-only. Cannot co-describe one entity. | Graph-separated facts coexist (KEY SHARED FACT); index-driven union surfaces them (`dkg-query-engine.ts:517,576`); each author retracts their own KA. | **Model 2** — Model 1 structurally cannot co-describe one entity (Rule 4 / SPEC:129). |
| **Reads & team curation** | Deterministic reads; a canonical KA can be team-governed via a Safe (RFC-45 §5). Drops per-quad context. | Non-deterministic reads (competing KAs reconciled by convention); keeps per-quad context. | **Depends** — curated single truth vs. expressive multi-source truth. |
| **Censorship / capture resistance** | One owner gatekeeps the canonical entity; to contribute against their wishes you publish a separate linking entity readers must follow (SPEC:129). Capture-resistant *for the owner*, capture-prone for third parties. | Anyone attaches a first-class parallel KA; no per-entity gatekeeper in an open CG. | **Model 2** — structurally more open; Model 1 deliberately centralizes per-entity authority. |
| **Audit trail of a specific claim over time** | Single linear, owner-controlled version history per entity; superseded facts replaced in-place (prior versions live only on-chain). Full-restatement updates (GH842 §1a). | Branchy multi-source history: a new author mints a parallel KA rather than overwrite, so competing/temporal claims coexist as distinct auditable graphs. | **Depends** — simpler single audit vs. richer reconcile-it-yourself trail. |

**Cluster read:** Model 1 wins the *mental-model crispness* axis; Model 2 wins *collaboration, autonomy, contestability, and per-author retraction*. The split is a product thesis, not a quality gap: Wikidata-style canonical curation vs. nanopublication-style multi-source assertion.

## 2. Scalability & Performance

The decisive insight from the code: **"many named graphs" was never the real cost — *discover-by-scan* was.** Both models' point-read is O(KA) on the data. Today's killer is two whole-store `listGraphs()` scans (`dkg-query-engine.ts:517,576`, each a `SELECT DISTINCT ?g WHERE { GRAPH ?g {?s ?p ?o} }` per `oxigraph.ts:266-279` / `blazegraph.ts:176-182`) plus an N-way `GRAPH..UNION` (`dkg-query-engine.ts:2195-2198`) that grows with the node's *global* KA count and crashes Blazegraph. Model 1 eliminates discovery *structurally* (2 graphs forever, SPEC:168). Model 2 can eliminate it *by index* — resolving exact graph IRIs from an indexed `_meta` lookup instead of `listGraphs()`. **Do not let Model 1 win this cluster by default.**

| Dimension | Model 1 (exclusive-entity / 2-graph) | Model 2 (per-KA named graph) | Verdict |

Without it, the read is a STRSTARTS closure over an unbound `?s` = O(bucket) (`dkg-query-engine.ts:729-744`, filter at :732). `resolveKA` today still uses the O(bucket) STRSTARTS — the fast read is **unbuilt new work**. | O(1) resolve (exact graph IRI from indexed `_meta`) + O(KA) read. The 4th term *is* a native bound-graph index: `GRAPH <g> {?s ?p ?o}` hits the single-graph fast path (`dkg-query-engine.ts:438-439`) — no STRSTARTS, no backlink, no `_meta` join. | **Model 2** — both reach O(1)+O(KA), but Model 1 must materialize a new per-subject backlink and exclude it from 7 merkle sites (§10.1); Model 2 gets it from the 4th term for free. |
| **View-read ("all of agent X's working memory")** | One bucket + a server-injected `?ka prov:wasAttributedTo <agent>` filter in `_meta` (RFC-46 §5b, :513-519). No listGraphs, no UNION. But agent isolation becomes a query-time filter that *must* be non-strippable (§9) — a new ACL surface. | Index-driven: resolve agent→KA-graph list from `_meta`, union a *known small* list. Without it (today): `working-memory` resolves to a prefix (:80-83) → `discoverGraphsByPrefix`→`listGraphs` (:517) → N-way UNION (:2195). | **Model 1** — structurally one graph + one indexed filter; Model 2 still unions N agent-owned graphs (N = that agent's KA count). | **Cross-KA analytical query (join/aggregate across many KAs)** | All KAs share one data graph → a plain single-graph BGP. Nothing to enumerate. | O(#KA) graphs. High count is cheap *storage* (4th term is an indexed column); the cost was *enumeration*, not per-context storage. | **Depends** — Model 1 wins the count metric; whether the count *costs* anything is store-dependent (dictionary pressure on some Blazegraph/Neptune configs vs. just an index dimension on Oxigraph). |
| **The listGraphs() / N-way-UNION problem** | Removed *structurally*: nothing to enumerate (§2.1), every read on the single-graph fast path (:438-439). The Blazegraph nested-UnionNode crash (commits e73e1c28, a9184f7a, 88b7703e, d19af5f8) cannot recur. | Removable *by engine change*: replace `discoverGraphsByPrefix`→`listGraphs` (:517,:576) with indexed `_meta` resolution. Kills the scan — but multi-graph reads still build a UNION over the resolved list, so the fragility + `:499-506` rejection persist for true multi-KA reads. | **Model 1** — index-driven discovery genuinely removes the dominant cost (the scan, the prompt's claim holds), but *not* the UNION or the portability tax. Model 1 is strictly more portable on the read engine; Model 2 is fixable but retains a residual UNION cost. |
| **Write / publish cost (new KA)** | Insert into the shared bucket + write +1 `dkg:knowledgeAsset <ual>` backlink *per subject* (RFC §3.5) + `_meta` row. Backlink is net-new write volume and index churn every publish; all inserts target one hot graph. | Insert into a fresh per-KA graph + `_meta` row. No backlink (4th term carries membership). New graph is O(1); writes land on a fresh graph — no contention. | **Model 2** — Model 1 pays extra write volume + index churn + contention on one graph. | **UPDATE cost (extend an existing entity)** | Owner-only UPDATE re-seals and re-publishes the **whole owning KA** (RFC-45; SPEC:129). Caveat: trades for read-time fan-in over the entity's many KAs + N small on-chain anchors. |
| **DELETE cost** | Naive delete is O(bucket): `deleteBySubjectPrefix` is a STRSTARTS-over-unbound-`?s` UPDATE on all 3 adapters (`oxigraph.ts:287`, `blazegraph.ts:80`, `sparql-http.ts:167`), 14 call sites; HTTP backends pay 2× full-graph COUNT (`blazegraph.ts:78+:82`). | **Replication / sync / gossip volume** | Uniform bucket shape collapses 3 cardinalities to 1 (RFC §1). Publish broadcasts KA quads + backlink triples (full replication, SPEC:170). Sync diff must exclude `dkg:knowledgeAsset` (`sync-handler.ts:236,241`). | Same KA-quad volume minus the per-subject backlink. Sync already operates per-CG (`sync-handler.ts:84-142`); per-KA graphs add 4th-term IRIs but the diffed payload is identical. Model 1 adds small backlink triples but gains layer uniformity (a code-simplicity win, not a volume win). |
| **Merkle / RS-proof gather cost** | Gather = member-entity closure over the bucket. O(KA) only via the indexed backlink seek; today's gather still uses O(bucket) STRSTARTS (`ka-extractor.ts:246`). Every gather feeding the merkle **must exclude** `dkg:knowledgeAsset` — **7 sites** (RFC §10.1). Miss one → backlink leaks into the leaf set → consensus breaks. | Gather = the KA's named graph directly (`GRAPH <g> {?s ?p ?o}`) — O(KA), indexed, no STRSTARTS, no exclusion. Merkle boundary identical (`assertion-seal.ts:47-56`). | **Model 2** — same boundary, but Model 1's gather inherits O(bucket) STRSTARTS or a 7-site consensus-exclusion obligation; Model 2 gathers per-graph with no such obligation. Lower-risk and lower-cost. |
| **Index size (per-subject backlink vs nothing extra)** | Net-new: +1 `dkg:knowledgeAsset` triple per KA *subject* (root + every skolem child) + POS/GPOS entries (RFC §3.5). Across 100K KAs × k subjects = 100K·k extra indexed triples purely for membership. `_meta` also gains a row per KA. | Nothing extra: the 4th term already encodes membership in the store's native GSPO/GPOS index. | **Model 2** — the store indexes the 4th term regardless, so Model 1's backlink is strictly additional index volume reproducing what the 4th term already carried. |
| **Hot-spot / write contention** | All writes target one shared data graph per layer. On the production single-writer Oxigraph worker, writes serialize and a read can starve behind queued writes (issue #939). Concurrent updates to different entities still contend on the same graph + per-subject locks for shared subjects. | Per-KA graph gives natural write isolation: concurrent publishes of different KAs touch disjoint graphs. Single-writer-worker serialization still applies at the store level, but no shared-graph hot spot, no per-subject lock contention between KAs. | **Model 2** — real concurrency advantage. Caveat (grounded, bench header + #938/#939): on *today's* single-writer worker ALL writes serialize regardless of graph, so the win is partly masked now and fully materializes only with MVCC/out-of-process server (#938). A future-facing win. |
| **The 616ms-vs-0.05ms benchmark** | RFC §3.5 *claims* STRSTARTS closure = 616ms vs indexed seek ≈ 0.05ms at 100K KAs/bucket (~2,900× by 50K), on pinned Oxigraph 0.5.5. Presented as proof the backlink is a **hard prerequisite** — without it, Model 1's bucket point-read is *slower than today*. | Not subject to it: Model 2 reads `GRAPH <g> {?s ?p ?o}` (the indexed-seek side by construction, `:438-439`). It never incurs the STRSTARTS path Model 1 must engineer around. | **Model 2** — **VERIFICATION:** the 616/0.05 numbers are an RFC *claim*, not an executable in-repo bench (the actual `bench/store-read-latency.bench.ts` measures LIMIT-1/COUNT shapes; no STRSTARTS micro-bench found). The *direction* is sound (unbound STRSTARTS can't use an index; bound (p,o) can); the *magnitude* is unverified here. |
| **Behavior at 100K / 10M KAs** | Graph count stays 2 (SPEC:168) — no enumeration cliff. The single data graph grows to ~10M·k quads; point-read stays O(KA) IF the backlink index holds. Risk: one enormous graph concentrates all index pressure + write contention; the backlink index grows to ~10M·k entries. | Graph count = 100K/10M. Index-driven discovery keeps reads fine. Risk: dictionary pressure from 10M distinct graph IRIs (store-dependent); any *residual* `listGraphs()` (admin/metrics) becomes a 10M-row DISTINCT scan and is catastrophic — the §3.2:273 invariant forbids such scans, and Model 2 must audit none remain. | **Depends** — both viable when fully fixed. Model 1 has the *simpler invariant to hold* (no scan possible); Model 2 must *continuously prove* no scan crept back. Unfixed Model 2 (today's `:517,:576`) degrades O(#KA) and is the worse option at 10M. |
| **Graph-discovery (the original motivation)** | O(1) by construction — bucket URI is arithmetic from (cg, subGraph, layer); nothing to scan (§2.1, §3.2:273). | O(1) by *index* — resolve exact graph IRI(s) from `_meta` instead of `listGraphs()`. Replaces `SELECT DISTINCT ?g` (`:266`) with a bound-key seek. | **Tie** — both reach O(1); the prompt's core claim ("many graphs per se is not the cost; discover-by-scan was") holds. Difference is *engineering risk*: Model 1's O(1) is unconditional; Model 2's requires every discovery path to use the index and never fall back. |

**Cluster read:** Genuine divergence, not a Model-1 sweep. **Model 1 wins** graph-count, discovery-uniformity, cross-corpus analytics, replication uniformity, and per-agent view fan-in. **Model 2 wins** point-read (free vs. contingent backlink), the overlapping-KA query, write/update/delete cost, merkle-gather simplicity, index size, and write isolation. The benchmark and the listGraphs/UNION pain are real and load-bearing for both — and index-driven discovery, the actual lever, is available to either.

## 3. Correctness, Consensus, Verifiability, Provenance

| Dimension | Model 1 | Model 2 | Verdict |
|---|---|---|---|
| **Can it represent two KAs' differing facts about the same shared subject?** | **No.** One data graph; the read `?s ?p ?o FILTER(?s=root ‖ STRSTARTS genid)` (`dkg-query-engine.ts:736-744`) returns every triple of a subject regardless of author. Two differing assertions conflate. The model *forbids* the case via exclusivity (SPEC:129,534). | **Yes — in the pure per-KA-graph form.** KA-A's `<s> p o1` and KA-B's `<s> p o2` live in distinct graphs, distinguishable per-QUAD. *Note:* RFC-46's bucket variant does NOT preserve this — it reifies membership per-*subject* (`<s> dkg:knowledgeAsset <ual>`, §3.5:296), which it calls "deliberately coarser" (:339-342), re-conflating shared subjects. | **Model 2** — per-quad context is the only carrier that separates such facts (KEY FACT; `:736-744`). The win belongs to the *pure per-KA-graph form*, not RFC-46 bucketing. |
| **Is overlap a real requirement or an anti-pattern? (steelman Model 1)** | Treats overlap as a modeling error designed out. Cross-party knowledge is Wikidata-style: one item, sourced statements via owner update authority; a third party mints a NEW linking entity (`<myReview> schema:about <theirEntity>`, SPEC:129). One canonical entity, no conflicting copies. | Treats overlap as first-class: independent authors/sources/timepoints coexist distinguishably. Matches provenance-rich corpora where "who asserted what" must survive without a single owner mediating. | **Depends** — single-owner registry (agent profiles, code-structure KAs, RFC-45 §3) → exclusivity is a feature (SPEC:336 "exclusivity guarantees no other KA claims this rootEntity, so deletion is safe"). Multi-source graph (reviews, observations over time) → overlap is necessary. Two product theses. |
| **Merkle leaf reconstruction / consensus boundary** | Boundary = `skolemizeByEntity(quads).keys()` set in the seal (`assertion-seal.ts:47-56,:52`), NOT the graph IRI. With exclusivity, the closure yields exactly that KA's leaves. | Identical boundary (`:52`). RFC §10:729: bucket migration "changes the 4th term of each quad and nothing else"; merkle root byte-identical, attestation unchanged. | **Tie** — both scope by the same key set; EIP-712 signs a fixed struct, never the graph IRI (RFC:726). Seal is graph-layout-invariant in both (KEY FACT, holds in code). |
| **Can shared-subject conflation corrupt a read/merkle in Model 1?** | Only if exclusivity is **violated.** A permissive path letting two KAs share a rootEntity makes the closure read (`:736-744`) return the UNION of both KAs' triples; `skolemizeByEntity` over that union yields a leaf set neither seal committed to — silent merkle/read corruption. The invariant is load-bearing for *correctness*, not tidiness. | Per-KA-graph form immune: read scoped to one graph IRI, so even same-named subjects don't cross-pull. (RFC-46 bucket form re-incurs Model 1's exposure.) | **Model 2** — Model 1's read correctness is *conditional* on a publish-time invariant whose failure is silent and consensus-affecting; Model 2 makes it unconditional via the graph fence. Model 1's central correctness risk: storage cannot itself represent the separation. |
| **RS-proof (Random Sampling) leaf-gather correctness** | RS extractor seeds off `?ka dkg:partOf <ual>; dkg:rootEntity ?root` then genid closure over the data graph (`ka-extractor.ts:201-256`). With one KA/entity, gathered leaves equal the chain-committed set. No new obligation. | Per-KA-graph form: CONSTRUCT scoped to the KA's graph, unambiguous. RFC-46 bucket form: extractor would pick up the `dkg:knowledgeAsset` backlink, so §10.1 REQUIRES excluding it at site 7 (`ka-extractor.ts:243-246`) or the proof breaks. | **Model 1** — today's RS extractor already works under Model 1's layout and adds no exclusion obligation; RFC-46's form adds a NEW consensus-critical exclusion at 7 sites (2 feed the on-chain root). (*Pure* per-KA-graph Model 2 has no such obligation; the penalty is specifically RFC-46's.) |
| **Per-quad provenance ("who said THIS triple")** | Not answerable at triple level: all of a subject's triples share one graph, no per-author tag. Provenance is per-KA (`_meta` lifecycle: `prov:wasAttributedTo`, `assertion-seal.ts:174`). Coarse but unambiguous given exclusivity. | Per-KA-graph form answers it natively: the 4th term IS the KA → author via `_meta`. Two authors' claims about one subject remain attributable down to the quad. | **Model 2** — the named graph directly carries KA/author membership. Model 1 attributes only at entity/KA granularity, and only because exclusivity collapses "the subject's facts" to one author. |
| **Immutability / audit of a specific claim over time** | Claim updated by full restatement of its owning KA, owner-only (GH842 §1a; RFC-45). History = the chain's ordered root sequence. Superseded facts replaced in-place; prior versions live only on-chain. | Per-KA-graph form lets a new author mint a parallel KA rather than overwrite — competing/temporal claims coexist as distinct auditable graphs. Updates still full-restatement per KA (GH842 §1a). | **Depends** — Model 1: single linear owner-controlled history (simpler). Model 2: branchy multi-source history (richer, reader reconciles). Neither more "immutable" — both restate fully. |
| **Risk of one KA's update silently changing another KA's data** | Within the invariant, low at representation level (no "other KA"). But the materialization-race class (GH842) lives in the shared data graph; cross-KA blast radius from a scope bug is wider — everything shares one graph (RFC §12.2 "Co-tenant blast radius"). | Per-KA-graph form: an update is confined to its own graph IRI — strong physical isolation. RFC-46 bucket form GIVES THIS UP: "a bug in the delete/closure scope corrupts neighbours in the bucket, not an isolated graph" (RFC §12.2:795). | **Model 2** — pure per-KA graphs contain a closure/delete bug; Model 1 (and RFC-46 buckets) put co-tenants in one graph, widening blast radius (the RFC concedes this, :795-796). The GH842 race itself is storage-model-orthogonal, but co-tenancy widens it. |
| **Correctness of the UAL-backlink seek under one-entity-one-KA** | The backlink seek is correct *precisely because* no subject belongs to two KAs: `?s dkg:knowledgeAsset <ual>; ?s ?p ?o` returns exactly that KA's triples — O(KA) POS seek (RFC §3.5:322-328). | In the genuinely-overlapping form there's no bucket, so the question doesn't arise — the graph IRI is the seek key. If you bucketed overlapping KAs + added the backlink, a shared subject would carry two backlinks and the projection would over-return BOTH KAs' triples — the carve-out would be **wrong**. | **Model 1** — the cleanest expression of the fundamental tension: the cheap indexed seek is a Model-1-shaped optimization, correct ONLY under exclusivity. You can have the cheap indexed seek OR overlap, not both. |
| **Self-consistency: does storage ENFORCE the invariant it depends on?** | Enforced only at publish-admission (reject existing rootEntity, SPEC:129,534) — storage can't represent a violation distinctly, so a missed check is silently corrupting. Correctness by convention + gate, not by construction. | Per-KA-graph form correct **by construction**: the fence physically separates KAs whether or not any check runs. RFC-46 bucket form moves back toward by-convention (7-site exclusion + exclusivity). | **Model 2** — correctness-by-construction is more robust than correctness-by-invariant-plus-gate. Model 1 concentrates correctness in one admission check whose failure is silent and consensus-affecting. Architectural-robustness call. |
| **Verifiability of the membership index itself** | Membership is implicit (subject-prefix closure) + `_meta` `dkg:rootEntity` rows (`assertion-seal.ts:58-69`). Seal commits the entity SET, so membership-by-entity is anchored; but it cannot attest "this specific triple is KA X's" beyond the closure. | Per-KA-graph: membership = graph IRI, also not in the merkle (merkle is over `skolemizeByEntity` keys, not the 4th term). RFC-46's `dkg:knowledgeAsset` backlink is a data triple but is *excluded* from the merkle at all 7 sites — also unattested. | **Tie** — in both, the membership carrier (graph IRI or subject-prefix/backlink) is OUTSIDE the merkle leaf set; per-triple membership is equally non-attestable. Verification rests on the entity-set closure either way. |

**Cluster read:** On the single most important correctness axis — representing two KAs' differing facts about a shared subject — **Model 2 (pure per-KA graph) wins decisively** and Model 1 structurally cannot; Model 1 *forbids* the case rather than solving it. On the consensus core (merkle reconstruction, seal invariance, per-triple membership attestability) the two are a **tie**. Model 1's residual liabilities: read correctness conditional on a silent, consensus-affecting publish-time invariant, and (under bucketing) widened co-tenant blast radius. RFC-46's residual liability: a new 7-site consensus-critical exclusion, 2 sites feeding the on-chain root. The fairness point: RFC-46 bucketing is correctness-equivalent to Model 1 on the shared-subject axis — it is not a path to *both* overlap and cheap reads.

## 4. Query Capability, Store Portability, RDF/Standards Alignment

| Dimension | Model 1 | Model 2 | Verdict |
|---|---|---|---|
| **GRAPH ?g membership ("which KA?" as a free quad fact)** | Lost: all KAs share one data graph; the 4th term no longer identifies a KA. Re-materialized as a per-subject backlink `<s> dkg:knowledgeAsset <ual>` (RFC §3.3/§3.5:293-328). | Free and native: the 4th term (per-KA graph IRI) carries membership per-quad; `resolveKA`/SWM/WM reads already use `GRAPH ?g` (`:694-703`; carve-out `dkg-publisher.ts:1238-1247`). | **Model 2** — RDF 1.1 quads give membership at zero schema cost; Model 1 reintroduces it as data (RFC §3.6:339 calls the backlink a "reification of graph membership"). |

**Cluster read:** A clean split. **Model 2** is the more standards-native design (real RDF 1.1 named graphs → `GRAPH ?g` membership, per-graph DROP/ACL, PROV/nanopub provenance "for free," and the only model that keeps overlapping shared-subject facts distinguishable). Its decisive liability is *operational, not representational*: discover-by-scan + N-way UNION that breaks Blazegraph and rejects cross-graph modifiers. **Model 1** inverts this: portable single-graph analytics across every SPARQL 1.1 engine, O(1) discovery — but it forfeits the quad features, reintroduces membership as a reification triple, loses atomic per-KA DROP and per-graph ACL, and cannot represent overlap. Fairness point the prompt's framing slightly understates: Model 2's portability problem is the UNION, not named graphs — an index-driven single-bucket-per-read variant would neutralize most of the gap while keeping the quad features. Neither model needs RDF-star.

## 7. "Best When"

**Model 1 (exclusive-entity / 2-graph) is the right choice when** the product is a single-owner *canonical registry* — agent profiles, code-structure KAs, a Wikidata-style "one item per entity" knowledge base where authoritative update authority and a single linear audit trail are features, not constraints. It shines when whole-corpus analytical queries (aggregate/join across all KAs) are a primary, high-frequency workload and must run portably across every SPARQL 1.1 engine without UNION fragility; when per-agent view reads dominate and benefit from single-bucket fan-in; when minimal storage footprint and an *unconditional* no-scan invariant (provably nothing to enumerate) are operationally valuable; and when the team is willing to accept entity-exclusivity as a hard product rule, treat key-loss as an account-level (Safe/EIP-1271) discipline, and pay the migration + 7-site consensus-exclusion + new-security-filter cost to get there. Model 1 is the correct choice *if and only if* overlap is genuinely out of scope.

**Model 2 (overlapping KAs / per-KA named graph) is the right choice when** independent parties, sources, or timepoints must assert about the same entity and "who said what" must survive at the quad level — multi-source corpora, reviews/claims/observations, provenance-rich graphs aligned with PROV/nanopublication patterns. It shines when permissionless contribution and contestability matter (no per-entity gatekeeper, no key-loss chokepoint); when defense-in-depth privacy (physical graph fence + query deny) is a security requirement; when incremental knowledge accretion is frequent (mint a small new KA in O(edit) rather than re-seal the whole owning KA in O(KA-size)); when atomic O(1) per-KA delete and per-KA write isolation matter; and when the team wants the lower-effort, lower-blast-radius, *reversible* default — Model 2 retains the per-quad context that lets it still become Model 1 later, whereas Model 1 forecloses Model 2. Note Model 2 *requires* shipping index-driven discovery to drop the `listGraphs()` scan; without that fix it degrades O(#KA) and is the worse option at scale.

## 8. Decision Lens

Three questions resolve the fork; answer them before counting dimensions:

1. **Do independent parties need to assert *differing* facts about the *same* entity, with per-source attribution preserved?**
   - **Yes →** only Model 2 (pure per-KA graph) can represent it; Model 1 (and RFC-46 bucketing) structurally cannot — they *forbid* the case. This single answer can decide everything.
   - **No (one-item-per-entity is the target) →** Model 1's exclusivity becomes a feature (clean deletion, single audit, clear update authority), and most of Model 2's correctness/governance edge goes moot.

2. **Is the dominant query workload whole-corpus analytics (aggregate/join across all KAs), or per-KA / per-agent scoped reads?**
   - **Whole-corpus analytics across heterogeneous engines (esp. Blazegraph/Neptune) →** Model 1's single-graph scan is decisively more portable and avoids the N-way UNION fragility. (Index-driven Model 2 narrows but doesn't equal it.)
   - **Per-KA / per-author reads, multi-source views →** Model 2's native `GRAPH <g>` reads are O(KA) for free; Model 1 must build and consensus-protect a per-subject backlink to match.

3. **Is the v10 SPEC's single-canonical-entity governance a fixed requirement, and how much migration/consensus/security risk is acceptable now?**
   - **Spec is fixed; team accepts the rework →** Model 1 is what the spec targets (SPEC:161-168,:129); pay the migration, the 7-site consensus-exclusion, and the new unstrippable-ACL-filter to realize it.
   - **Spec is revisable; minimize risk and keep options open →** Model 2 is keep+optimize-discovery (swap two `listGraphs()` scans), preserves reversibility, and touches neither the consensus boundary nor the security trust-boundary. The lower-regret default — adopt it now, and Model 1 remains a future option; adopt Model 1 now, and Model 2 is foreclosed.

**One-line synthesis:** if overlapping multi-source assertions are a product requirement, choose Model 2 (pure per-KA named graph); if a single-owner canonical-entity model is acceptable, Model 1 (optionally with RFC-46 bucketing for read cost) delivers exactly the spec's intended properties — and in that world, overlap is intentionally out of scope and most of Model 2's advantage becomes moot. RFC-46 is *not* a way to have both.
