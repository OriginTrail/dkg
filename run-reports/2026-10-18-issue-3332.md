The final implementation passed **2,211 publisher tests in 120 files**. A subsequent test-only review revision added one independently verified negative case; the updated pull suite passes all 72 tests. Extended live checks also found a **pre-existing** finalized-unpublished-edit/discard failure, reproduced on the unchanged base branch. This report does not claim that adjacent failure is fixed or that every lifecycle path is regression-free.

## Repeatable fault/restart recipe

Follow the dkg-testnet macOS runbook and claim a prepared batch before using its keys. Use a fresh isolated home and synthetic graph/name; do not reuse this released home without reacquiring its original batch.

1. Build the checkout, verify native SQLite, and copy exactly the four wallet/config bundle files. Disable updates, enable API authentication, and point the isolated config to a dedicated quad-enabled Blazegraph namespace (`quads=true`, `truthMaintenance=false`, `NoAxioms`). Verify chain/Hub/token bindings and balances.
2. Create a private local context graph and save its subscription so it rehydrates after restart. Create a named draft with one synthetic public triple. This run seeded one synthetic private triple through `PrivateContentStore.storeKnowledgeAssetPrivateDraftTriples`; the named HTTP writer exposes public authoring only.
3. Finalize through the native API, enqueue native async SWM share, and wait for terminal `succeeded`. Save the exact UAL/version, source root, and resolved SWM head locally.
4. Start the owned daemon with a local Node preload that wraps `BlazegraphStore.prototype.deleteByPatternWithoutCount`. Match only this fixture's active-seal subject and metadata graph. Permit four real calls, then throw before the fifth and disable the fault. Do not intercept recovery-archive writes or another asset.
5. Call native `wm/pull-from` with `layer: swm` and `onConflict: reject`. Require the injected failure; read-only inspection must prove the four missing fields, a complete private archive, and unchanged exact SWM source.
6. Stop the owned daemon, restart its Blazegraph container, then start the same home without the fault hook. Wait for authenticated API readiness and the saved graph subscription.
7. Repeat the exact pull. Require 200, identical KA/version, and canonical equality of both public and private WM content. A second successful-response replay must return `WM_DRAFT_CONFLICT` under reject semantics.
8. Inspect share/VM jobs and finalization recovery, stop owned processes/listeners, reconcile all signer nonces and submitted transactions, and release the matching claim only when quiescent.

The local executed harness is retained under `.scratch/3332/`: `prepare-live.mjs`, `fault.mjs`, `inject-live.mjs`, `recover-live.mjs`, `api.mjs`, and `balances.mjs`. It uses the native auth loader without printing tokens. Its fixture IDs and logs are not needed in public evidence.

## Limits and follow-up

The extended sequence `share -> pull -> edit -> finalize (still unpublished version 1) -> discard -> pull` can replace/lose the usable prior recovery commitment and then fail source validation. A temporary deterministic test against unchanged base `2361a863d` reproduced it; the failure is not caused by this PR. The affected synthetic live fixture was left intact for diagnosis rather than repaired by direct metadata mutation. The final partial-clear run used a fresh synthetic name.

Response loss after seeding is intentionally not an idempotent-success contract: reject mode reports a draft conflict. Public equality alone cannot prove private WM is complete or empty. This PR adds no read-only recovery-readiness or private-draft-proof HTTP endpoint. Clients must not treat a descriptor or a public-only source commitment as authority to overwrite an unknown private draft.

The public RPCs reported historical-block/log-range availability errors during background indexing; this did not prevent the tested SWM share, fault or recovery.

No live VM publish was attempted: this run targets the reported SWM/private-context recovery. VM source integrity and independent VM validation were exercised in the publisher/store tests.
